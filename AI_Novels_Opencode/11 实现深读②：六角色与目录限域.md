# 11 实现深读②：六角色与目录限域

> [!abstract] 这篇讲什么
> 上一篇（[[10 实现深读①：作品存储与唯一提交服务]]）讲了"作品 = 目录 + git"。这篇讲"六角色"——**谁能在哪些目录写，是被代码强制的**，不是靠 AI 自觉。全部基于真实源码：`packages/novel-core/src/role.ts`、`packages/novel-core/src/work/role-permissions.ts`。生词点 [[09 名词解释]]。

---

## 0. 为什么需要角色限域（人话问题）

六角色 = 1 个主编（主管）+ 5 个专家（设定/大纲/细纲/正文/校对）。如果"设定 agent"偷偷去改了"正文"，世界观就串味了。所以每个角色有**可写目录白名单**：设定 agent 只能写 `设定/**`，正文 agent 只能写 `正文/**`。

> [!tip] 复习：[[09 名词解释#六角色 / 主编 / 专家会话 / 委派]]、[[09 名词解释#权限 / 限域（scoped permission）]]。

## 1. `role.ts` 逐函数讲解

### 1.1 `ALL` / `SUPERVISOR` / `SPECIALISTS`（role.ts:2,4,6）—— 花名册

```ts
export const ALL = ["主编", "设定", "大纲", "细纲", "正文", "校对"] as const
export const SUPERVISOR = "主编"
export const SPECIALISTS = ["设定", "大纲", "细纲", "正文", "校对"] as const
```

- **`ALL`**：六个角色名的数组。
- **`SUPERVISOR`**：常量 `"主编"`，代表主管。
- **`SPECIALISTS`**：五个专家名数组。
- **关键点 `as const`**：这是 TypeScript 的"常量断言"。加了它，数组不再是普通的 `string[]`，而是精确的 `["主编","设定",...]` 字面量类型。配合下面的类型别名，能让你传错角色名时**编译期就报错**，而不是运行时才炸。

### 1.2 `Name` / `Specialist`（role.ts:8,10）—— 类型别名

```ts
export type Name = (typeof ALL)[number]
export type Specialist = (typeof SPECIALISTS)[number]
```

- **`Name`**："六角色中的任意一个"的类型。
- **`Specialist`**："五专家中的任意一个"的类型。
- **用途**：后面所有函数的参数用这些类型，等于给角色名加了"只能填这六个值"的保险。

### 1.3 `WRITE_SCOPE`（role.ts:17）—— 每个角色能写哪些目录

```ts
export const WRITE_SCOPE: Record<Name, readonly string[]> = {
  主编: ["memory/**"],
  设定: ["设定/**", "memory/**"],
  大纲: ["大纲/**", "memory/**"],
  细纲: ["细纲/**", "memory/**"],
  正文: ["正文/**", "memory/**"],
  校对: ["memory/**"],
}
```

**这是整篇最核心的一张表。** 含义（每行 = 该角色允许写的目录 glob）：

| 角色 | 可写目录 | 说明 |
|---|---|---|
| 主编 | `memory/**` | 只写共享记忆区 |
| 设定 | `设定/**` + `memory/**` | 创作目录归自己，+共享记忆 |
| 大纲 | `大纲/**` + `memory/**` | 同上 |
| 细纲 | `细纲/**` + `memory/**` | 同上 |
| 正文 | `正文/**` + `memory/**` | 同上 |
| 校对 | `memory/**` | 只写共享记忆区（不创作） |

> [!note] 为什么 `memory/**` 所有人都可写？
> `memory/` 是"已验证事实"的共享记录区（见 [[10 实现深读①：作品存储与唯一提交服务#1. 一个作品长什么样]] 里的 `MEMORY_DOCUMENTS`）。设定 agent 发现的"主角年龄=17"这类事实，其他角色都要读，所以开放成**唯一共享写面**；而创作目录（设定/大纲/细纲/正文）严格各归各的专家。

### 1.4 `normalizeWorkPath`（role.ts:27）—— 路径归一化

```ts
export const normalizeWorkPath = (filePath: string) =>
  filePath.replaceAll("\\", "/").replace(/^\.\//, "").replace(/^\/+/, "")
```

- **做什么**：把任意路径统一成"作品相对路径"标准形式——反斜杠 `\` 全转正斜杠 `/`，去掉开头的 `./` 和多余的 `/`。
- **为什么**：Windows 用 `\`、别的用 `/`；有的路径带 `./` 前缀。不统一就无法和 `WRITE_SCOPE` 里的 `设定/**` 做字符串比较。先归一化，后面比较才稳。

### 1.5 `matchesWriteScope`（role.ts:30）—— 单个 scope 匹配（内部函数）

```ts
const matchesWriteScope = (filePath: string, scope: string) => {
  if (scope.endsWith("/**")) {
    const dir = scope.slice(0, -3)
    return filePath === dir || filePath.startsWith(`${dir}/`)
  }
  return filePath === scope || filePath.startsWith(`${scope}/`)
}
```

- **做什么**：判断 `filePath` 是否落在 `scope` 内。
  - 若 `scope` 以 `/**` 结尾（如 `设定/**`）：表示"该目录及其所有子目录"。检查 filePath 是否等于 `设定` 或 以 `设定/` 开头。
  - 否则：精确等于 `scope`，或位于 `scope/` 之下。
- **大白话**：这是项目自己对 glob（`**` 通配）的最小实现——只支持这一种通配，够用且简单。

### 1.6 `mayEditPath`（role.ts:43）—— 角色能否写某文件（同步检查镜像）

```ts
export const mayEditPath = (role: string, filePath: string) => {
  const normalized = normalizeWorkPath(filePath)
  if (!normalized) return false
  if (!(ALL as readonly string[]).includes(role)) return false
  const scopes = WRITE_SCOPE[role as Name]
  if (scopes.length === 0) return false
  return scopes.some((scope) => matchesWriteScope(normalized, scope))
}
```

**逐行走读**：
1. 先 `normalizeWorkPath` 归一化路径。
2. 空路径 → 直接 `false`。
3. 角色名不在 `ALL` 里 → `false`（非法角色）。
4. 取该角色的 `WRITE_SCOPE`；若没有任何 scope → `false`。
5. 任一 scope 匹配成功 → `true`，否则 `false`。

> [!warning] 关键设计说明（role.ts:38-42 注释，务必记住）
> `mayEditPath` **只是同步检查的"镜像"**，用于 UI 提示（hints）和测试。**真正的运行时强制是 OpenCode 的 `PermissionV2`**，由应用自有的 Agent 定义承载。
> **不要**在"作者编辑器"或"CommitService"里把它当第二道写门来用。
> 也就是说：角色能不能写那个目录，最终是 OpenCode 权限引擎拦的，而不是 novel 代码里再拦一道。

> [!tip] 呼应铁律
> [[01 项目是什么#设计铁律]] 说"确定性归系统"。权限强制属于"确定性"——所以交给 OpenCode 权限系统（系统层），novel 不重复造轮子（对照 [[09 名词解释#权限 / 限域（scoped permission）]]）。

### 1.7 `AGENT_ID`（role.ts:53）—— 角色名 → OpenCode agent id

```ts
export const AGENT_ID: Record<Name, string> = {
  主编: "主编", 设定: "设定", 大纲: "大纲", 细纲: "细纲", 正文: "正文", 校对: "校对",
}
```

- **做什么**：把产品角色名映射到 OpenCode 内部的 agent id。
- **注释要点**：agent id = 应用自有的 `.opencode/agents/` 目录下的 **markdown 文件名**（例如 `设定.md`）。
- **大白话**：六角色不是抽象概念，每个都对应磁盘上一个真实的 agent 定义文件，里面装着它的**提示词**和**权限**。主管要委派"设定专家"去干活，就是按这个 id 找到那个 agent 定义。

## 2. `role-permissions.ts` 逐函数讲解

### 2.1 `editRulesFromWriteScope`（role-permissions.ts:2）—— 把白名单翻译成 OpenCode 权限规则

```ts
export const editRulesFromWriteScope = (scopes: readonly string[]) => {
  if (scopes.length === 0) return [{ action: "edit", resource: "*", effect: "deny" as const }]
  return [
    { action: "edit", resource: "*", effect: "deny" as const },
    ...scopes.map((resource) => ({ action: "edit", resource, effect: "allow" as const })),
  ]
}
```

**逐行走读**：
1. 若 `scopes` 为空（这角色啥都不能写）→ 直接返回一条 `{ action:"edit", resource:"*", effect:"deny" }`：全部拒绝。
2. 否则：先放一条 **`deny *`**（默认全拒绝）作为兜底，再对每条 scope 生成一条 `{ action:"edit", resource:<scope>, effect:"allow" }` 白名单。

- **为什么"先 deny 后 allow"**：这是安全设计的经典模式——默认拒绝一切，只把白名单里的放行。即使哪天漏配了某条，**也不会变成全盘开放**（fail-closed）。
- **它服务哪条链路**：这是"把 `WRITE_SCOPE` 翻译成 OpenCode `PermissionV2.evaluate` 能执行的规则"的桥梁。角色限域最终落地在 OpenCode 权限引擎，而不是 novel 代码里再拦。

## 3. 把这条链路串起来（业务视角）

完整业务流：**创建作品/会话时** → 取该角色的 `WRITE_SCOPE`（role.ts:17）→ 用 `editRulesFromWriteScope` 转成 `PermissionV2` 规则（role-permissions.ts:2）→ 注入该 agent 的 OpenCode 定义（即 `.opencode/agents/设定.md`，由 `AGENT_ID` 定位）→ **运行时 OpenCode 拦截任何越界写**。

两层防护，职责不同：
- **OpenCode 权限引擎**：管"这个角色能不能写那个目录"（角色限域）。
- **CommitService 的 `assertRelativePath`**（见 [[10 实现深读①：作品存储与唯一提交服务#3. AI/作者"写文件"到底做了什么]]）：管"路径有没有穿越出作品根目录"（防路径穿越）。

> [!note] 一句话总结
> 六角色的"目录限域"不是一句提示词，而是 `WRITE_SCOPE` 这张表 → `editRulesFromWriteScope` 翻译成 OpenCode 权限规则 → 由 OpenCode 在运行时硬拦。novel 代码本身**不**再写第二道权限门（那是被明确禁止的技术债，见 [[09 名词解释]] 里"严厉禁止"中的"绕过原生能力自造轮子"）。
