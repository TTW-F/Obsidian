# 09 名词解释（新手必读）

> [!warning] 怎么用这篇
> 这是给**完全零基础实习生**的词典。读其他笔记时遇到看不懂的词，直接点链接跳过来（如 [[09 名词解释#monorepo]]）。每个词都先用大白话+比喻，再讲"在本项目里指什么"。**看其他笔记前先扫一遍本篇。**

---

## 一、代码 / 仓库相关（最基础）

### monorepo
**大白话**：把很多个"小项目（包）"塞进**同一个 git 仓库**里统一管理。
**比喻**：普通仓库像一个文件夹里放一个 App；monorepo 像一个大楼，里面有很多公司（包），但共用一部电梯（统一的构建/测试/依赖管理）。
**本项目**：`F:\AI_Novels_OpenCode` 就是 monorepo，里面有 `packages/novel-core`、`packages/novel-server`、`apps/novel-web` 等几十个包。

### fork（复刻 / 分叉）
**大白话**：把别人公开的代码仓库**完整复制一份**到自己名下，之后可以随便改，不影响原仓库。
**本项目**：团队从开源项目 OpenCode fork 出来，在它的基础上加网文功能。原 OpenCode 还在独立更新。

### git 仓库 / repo
**大白话**：用 git 这个工具做"版本历史"的文件夹。每次 `commit`（提交）就存一个快照，能回滚、能看谁改了什么。
**本项目**：整个 `AI_Novels_OpenCode` 是一个 git 仓库；每个"作品"也是各自独立的 git 仓库。

### HEAD
**大白话**：git 里"当前已经正式保存的最新版本"。
**本项目**：作者 `Keep` 某个文件 = 把它 `commit` 进 git，于是 HEAD 更新成正式内容。AI 还没被作者确认的改动**不在** HEAD 里。

### 工作区（working tree / 工作目录）
**大白话**：你电脑上文件夹里**当前真实看到的文件**（可能比 HEAD 多了一些没保存的改动）。
**本项目**：AI 和作者写的都是"工作区"这一份文件。工作区相对 HEAD 的差，就是待作者裁决的 diff。

### commit（提交）/ diff（差异）
**大白话**：`commit`=按下"保存并留档"；`diff`=对比"现在"和"上次保存"差了哪些行。
**本项目**：`Keep`=按文件 commit；`Undo`=把文件恢复成 HEAD。三栏 diff 界面就是并排看 HEAD / 工作区 / 合并预览。

### branch（分支）
**大白话**：在同一份代码上开出一条"平行时间线"，互不干扰，最后可合并。
**本项目**：默认用 `dev` 分支开发；不要直接动 `main`（本仓可能没 main）。

## 二、本项目专有概念

### OpenCode
**大白话**：一个**开源的 AI 编程助手**（类似 Cursor/Claude Code），本来是给人写代码用的。
**本项目**：我们没自己造引擎，而是把它 fork 过来当"底座"，在上面套了一层网文创作功能。所以仓库里 90% 的代码是 OpenCode 原装的。

### Session（会话）/ Session V2
**大白话**：`Session`=AI 和作者"一次连续的对话+干活过程"的运行实例；V2 是它第二版实现，带持久化（关掉再开能恢复）。
**本项目**：每个 Agent 的工作都跑在一个 OpenCode Session 里。我们不直接改它，而是"桥接"它。

### sdk-next
**大白话**：`SDK`=Software Development Kit（软件开发工具包，把底层能力打包好给你调用）；`sdk-next` 是本项目里一个**特定包名**，等于"下一代客户端工具包"。
**本项目**：`packages/sdk-next` 用来**在进程内嵌入** OpenCode 的 Session 能力，不让它另起一个服务进程。

### agent（智能体）/ 多 Agent
**大白话**：`agent`=一个被赋予角色和工具的 AI 工作者（能自己决定调用哪些工具完成任务）。`多 Agent`=好几个各司其职的 agent 协作。
**本项目**：六角色 = 1 个主编(主管) + 5 个专家（设定/大纲/细纲/正文/校对）。主管协调专家。

### skill（技能包）
**大白话**：给 agent 加载的"方法论说明书"文件，按需读取，告诉它某种写作/任务该怎么干。
**本项目**：作者可配置作品守则（AGENTS.md 式）和写作 Skills 按需加载。

### 六角色 / 主编 / 专家会话 / 委派
- **六角色**：主管(主编)+五专家，见 [[02 领域词汇表]]。
- **委派**：主管给某个专家发"有署名的工作请求"，专家做完回传结果——这是默认协作路径，不是随便丢个匿名小弟。
**大白话**：像主编把"写第三章"派给正文专家，专家干完向主编汇报。

### 编排（orchestration）
**大白话**：怎么安排多个 agent 谁先谁后、怎么传话。
**本项目**：首期不锁死具体编排方式（常驻 vs 委派），先跑通体验再定最简实现。

### 防剧透
**大白话**：防止 AI 在正文中提前写出"还没揭晓的未来剧情"。
**本项目**：**故意不做成系统功能**，靠四层软约束：设定写法 + 正文提示词纪律 + 校对检查 + 作者看 diff 自己裁判。

### 契约矩阵（contract matrix）
**大白话**：一份"前端和后端通信的接口长什么样"的对照检查表（每个端点、每个事件的字段/格式）。
**本项目**：因为前端是从另一套原型照搬过来的，所以后端必须严格对齐这份契约，否则前端解析报错。

### 唯一提交服务
**大白话**：所有"写文件"的动作（作者保存/Keep/Undo/删除/改名）都**只能从这一道门进**，进门后统一触发索引更新。
**本项目**：`packages/novel-core/src/git/commit-service.ts`。

### 作品（Work）
**大白话**：作者写的一本书 = 一个文件夹 + 一个 git 仓库，里面按大纲/细纲/正文/设定等子目录组织。
**本项目**：详见 [[02 领域词汇表]]。

## 三、前后端通信（怎么传数据）

### HTTP / API
**大白话**：`HTTP`=浏览器/程序之间请求数据的协议；`API`=程序对外提供的"办事窗口"（你按格式发请求，它回你数据）。
**本项目**：`novel-server` 提供 Workbench HTTP API，前端 `novel-web` 调用它。

### SSE（Server-Sent Events）
**大白话**：服务器**单方面、持续地**往浏览器推消息的通道（比如 AI 边写边把进度推过来）。和聊天流差不多。
**本项目**：OpenCode 的 Event V2 流 → 我们映射成公开 SSE 事件 → 前端实时渲染。

### 幂等（idempotency）
**大白话**：同一个请求发两次，结果和发一次一样，不会重复生效。靠 `Idempotency-Key`（幂等键）识别重复。
**本项目**：命令总线要求幂等，防止网络重发导致重复 Keep/写。

### 进程内嵌入（in-process embedding）
**大白话**：不另外开一个程序，而是**直接在当前程序里调用**另一个库的能力。
**本项目**：`sdk-next` 被嵌进 `novel-server` 进程里跑 OpenCode Session，而不是另起 `opencode serve`。

## 四、AI / 模型相关

### LLM（大语言模型）/ Provider
**大白话**：`LLM`=会写会聊的 AI 模型（如 GPT、Claude）；`Provider`=卖模型的厂家/接口（OpenAI、Google 等）。
**本项目**：作者可自己配置 Provider（base URL + API key），不被锁死单一供应商。

### 权限 / 限域（scoped permission）
**大白话**：限制某个 agent **只能改哪些目录**。
**本项目**：设定 agent 只能写 `设定/**`，正文 agent 只能写 `正文/**`——角色边界在系统层强制，不只靠提示词。

### 提示词（prompt）
**大白话**：你给 AI 的指令/人设文字。
**本项目**：六角色的 `.opencode/agents/*.md` 就是各自的提示词资产。

## 五、Obsidian 笔记术语（你已经在用，但统一一下叫法）

### vault（笔记库）
**大白话**：Obsidian 的一个笔记文件夹（本项目 onboarding 笔记就放在 `D:\Git_Obsidian\Obsidian\AI_Novels_Opencode`）。

### wikilink（内部链接）
**大白话**：用 `[[笔记名]]` 指向 vault 内另一篇笔记，点击即跳转；改文件名 Obsidian 自动更新所有链接。
**例**：`[[01 项目是什么]]` 会跳到那篇笔记。

### frontmatter（笔记头）
**大白话**：每篇笔记最上方 `---` 包裹的配置块，写 `title`/`tags`/`status` 等元数据（不影响正文阅读）。

### MOC（Map of Content，内容地图）
**大白话**：一篇"目录型"笔记，用链接把相关笔记串起来，作为某主题的入口。本 vault 的 `00 项目导航 MOC` 就是。

### callout（高亮框）
**大白话**：`> [!note]` 这类带图标和底色的信息块，用来强调重点/警告。本 vault 用 `> [!danger]` 标红线。

### canvas（画布）
**大白话**：Obsidian 里把笔记变成"可拖拽节点 + 连线"的可视图。本 vault 的 `项目全景.canvas` 就是。

### bases（表格视图）
**大白话**：Obsidian 把带属性的笔记自动汇总成可筛选表格的功能（类似数据库视图）。可用于做需求票追踪。

### projection（投影）
**大白话**：前端把后端原始数据"按某种视角重新呈现"出来的结果。
**本项目**：`apps/novel-web/src/lib/*-projection.ts` 就是把 Agent 信息流投影成 UI（不是普通聊天记录）。

### 标签（tag）/ 标签树
**大白话**：`#onboarding` 这类标记，可搜索、可分层（`#nested/tag`）。本 vault 笔记都打了 `tags:`。

## 六、部署 / 多租户

### 多租户（multi-tenant）/ 租户隔离
**大白话**：一套系统服务很多用户（租户），但互相看不到对方数据。
**本项目**：每个作者的作品和 Session 严格隔离，跨租户访问返回 404。

### 验收环境
**大白话**：专门用来"跑测试确认没问题"的机器，和写代码的机器分开。
**本项目**：`192.168.31.35`（Ubuntu）是测试兼生产，**只跑不改**；代码只在本机 Windows 改。详见 [[07 机器拓扑与红线]]。
