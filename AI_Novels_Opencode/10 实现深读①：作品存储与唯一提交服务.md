# 10 实现深读①：作品存储与唯一提交服务

> [!abstract] 这篇讲什么
> 这是"实现深读"系列第 1 篇。**目标**：让你读懂项目最心脏的一块——一个作品怎么存进磁盘、作者怎么用 Keep/Undo 裁决。读完你能对着真实代码说出"Keep 背后到底敲了哪两条 git 命令"。
> 全部基于真实源码：`packages/novel-core/src/work-layout.ts`、`git/work-repository.ts`、`git/commit-service.ts`、`git/run.ts`。遇到生词点 [[09 名词解释]]。

---

## 0. 先认清要解决的人话问题

作者写小说，AI 也在写。两人改的是**同一份文件**。问题来了：AI 写的东西不能直接算"正式"，得作者点头。

所以系统把状态分成两层（见 [[09 名词解释#HEAD]] / [[09 名词解释#工作区（working tree / 工作目录）]]）：
- **工作区**：磁盘上当前真实的文件（AI 和作者改的都是它）。
- **HEAD**：已经 `commit`（正式保存）的版本。

作者点 **Keep** = 把某些文件从"工作区"升级成"HEAD 正式版"；点 **Undo** = 把某些文件退回 HEAD 版本。AI 永远不能自己动 HEAD——这就是铁律"作者即裁判"。

---

## 1. 一个作品长什么样（work-layout.ts）

> [!tip] 复习：[[09 名词解释#作品（Work）]] 说作品 = 目录 + git 仓库。

`work-layout.ts:11` 用一行数组定义了每个新作品必须有的**一级目录**：

```ts
export const TOP_LEVEL_DIRS = [
  "大纲", "细纲", "正文", "设定", "时间线", "伏笔", "素材",
  MEMORY_DIR,   // "memory"
  "meta",
] as const
```

**大白话**：新建作品时，系统自动建好这 9 个文件夹。作者/AI 把对应内容放进去：
- `大纲`、`细纲`、`正文` = 小说的骨架到成稿
- `设定`、`时间线`、`伏笔` = 世界观/时间线/伏笔账本
- `素材` = 素材库
- `memory` = 人物卡、伏笔账本、世界观、连贯性检查单（见 `MEMORY_DOCUMENTS`，`work-layout.ts:8`）
- `meta` = 作品元信息

> [!note] 为什么固定目录很重要
> 后面"六角色限域"就靠这些目录名：设定 agent 只能写 `设定/**`，正文 agent 只能写 `正文/**`（详见 [[11 实现深读②：六角色与目录限域]]，待写）。目录结构是整套权限的地基。

## 2. 一个作品是怎么"出生"的（work-repository.ts）

建作品分两步，**故意拆开**以加快响应：

### 第 1 步：只建文件夹，不碰 git（`stageWorkWorkspace`，`work-repository.ts:11`）
```ts
await mkdir(input.workRoot, { recursive: true })
await cp(input.skeletonRoot, input.workRoot, { recursive: true, force: true })
```
就是把模板目录 `templates/work-skeleton` 整个复制到作品目录。**这一步没有 git，所以极快（~10–20ms）。**

### 第 2 步：初始化 git 仓库（`finalizeGitRepository`，`work-repository.ts:28`）
```ts
await runGitRaw(workRoot, ["init"])          // 建 .git
// 把身份写进 .git/config，省掉两次 git config 调用
await runGitRaw(workRoot, ["add", "."])       // 把所有骨架文件加入暂存区
await runGitRaw(workRoot, ["commit", "-m", "init: work skeleton"])  // 第一次提交
```
关键点：**`git commit` 之后，HEAD 才诞生。** 在此之前 HEAD 不存在（仓库是空的）。这条 `init: work skeleton` 提交就是作品的"第 0 版正式内容"。

> [!tip] 复习：[[09 名词解释#commit（提交）/ diff（差异）]]。`git init`=把文件夹变成 git 仓库；`git add`=暂存；`git commit`=正式存档生成 HEAD。

## 3. AI/作者"写文件"到底做了什么（writeWorkspaceFile，work-repository.ts:195）

```ts
await awaitWorkGitReady(input.workRoot)   // 等第 2 步的 git 初始化完
const absolute = path.join(input.workRoot, normalized)
await mkdir(path.dirname(absolute), { recursive: true })
await Bun.write(absolute, input.content)  // 把内容写到磁盘文件
clearUncommittedPathsCache(input.workRoot)
```

**大白话**：写文件 = 直接把字符串写到磁盘上的 `.md` 文件。**注意：这一步完全没碰 git！** 文件只在工作区，没进 HEAD。所以 AI 写完，作者看到的还是"未提交改动"。

### 顺手学一个安全细节：防路径穿越
`work-repository.ts:200` 和 `commit-service.ts:14` 都有这段：
```ts
for (const segment of normalized.split("/")) {
  if (segment === ".." || path.isAbsolute(segment)) {
    throw new Error(`refusing path outside work root: ...`)
  }
}
```
**为什么**：如果有人传 `../../etc/passwd`，就能写到作品目录外面去。系统拒绝任何含 `..` 或绝对路径的相对路径——这是最基础的"不能越权改别人文件"防线。

## 4. Keep 是什么（keepPaths，work-repository.ts:164）

```ts
await runGit(input.workRoot, ["add", "--", ...input.paths])        // 暂存指定文件
await runGit(input.workRoot, ["commit", "-m", input.message, "--", ...input.paths])  // 提交指定文件
clearUncommittedPathsCache(input.workRoot)
```

**这就是 Keep 的全部真相**：对作者选中的每个文件执行 `git add` + `git commit`。提交后，这些文件从"工作区"进入 HEAD = 正式内容。

> [!note] 为什么按文件提交？
> `git commit -- <paths>` 只提交指定文件，其余未提交改动**留着不动**。这样作者可以"只 Keep 第三章，不 Keep AI 写崩的设定"——精细裁决的关键。

还有个高级用法 `acceptPartial`（work-repository.ts:171）：作者改了 AI 写的一半、接受另一半。做法是：先把"接受的部分"写回文件并 Keep，再把"剩下的部分"写回（不 Keep）。一行代码就实现了"部分接受"。

## 5. Undo 是什么（undoPaths，work-repository.ts:183）

```ts
for (const rel of input.paths) {
  const tracked = await runGit(input.workRoot, ["ls-files", "--", rel])  // 这文件在 HEAD 里吗？
  if (tracked.trim()) {
    // 在 HEAD 里：把它恢复成 HEAD 版本（工作区+暂存区都回退）
    await runGit(input.workRoot, ["restore", "--source=HEAD", "--staged", "--worktree", "--", rel])
  } else {
    // 不在 HEAD 里（纯工作区新建）：直接从磁盘删除
    await rm(path.join(input.workRoot, rel), { force: true })
  }
}
```

**大白话分两种**：
- 文件之前 Keep 过（在 HEAD 里）→ `git restore` 把它**还原成 HEAD 版本**（丢弃工作区改动）。
- 文件是 AI/作者新建、从没 Keep 过 → 直接从磁盘删掉。

> [!tip] 复习：[[09 名词解释#HEAD]]。`git restore --source=HEAD` = 用 HEAD 的版本覆盖当前文件。

## 6. 唯一提交服务（commit-service.ts）—— 所有写操作的"唯一一道门"

前面那些 `keepPaths`/`writeWorkspaceFile` 散落各处，如果谁都能直接调，就乱了。于是有了**门面（facade）**：

```ts
export const createCommitService = (indexSync?: IndexSyncHook) => ({
  write:  async (i) => { /* 校验路径 + writeWorkspaceFile + 通知索引 */ },
  keep:   async (i) => { /* 校验路径 + keepPaths        + 通知索引 */ },
  undo:   async (i) => { /* 校验路径 + undoPaths        + 通知索引 */ },
  rename: async (i) => { /* 校验路径 + 移动/改名         + 通知索引 */ },
  remove: async (i) => { /* 校验路径 + 删除              + 通知索引 */ },
  ensureDir: ...
})
```

三个设计要点（对应 [[09 名词解释#唯一提交服务]]）：

1. **统一入口**：所有"写"都走这里（`write/keep/undo/rename/remove`）。别处想改作品文件，必须经过它——保证没有第二条写路径绕过规则。
2. **每次都校验路径**：`assertRelativePath`（commit-service.ts:14）先挡掉 `..` 穿越，再动手。
3. **写完通知索引**：每次写/Keep/Undo 后调 `notify(indexSync, workRoot, paths)`（commit-service.ts:9）。这就是"写路径触发把工作区投影进检索索引"——搜得到刚写的内容，Undo 后索引立刻消失。

> [!warning] 为什么"唯一一道门"是铁律级别的设计
> 如果 A 模块直接 `Bun.write` 写文件、B 模块直接 `git commit`，哪天要加"写之前检查权限""写之后同步索引"就得改 N 处还容易漏。收敛到一道门，规则只写一次、必被执行。这是 [[01 项目是什么]] 里"确定性归系统"的具体落地。

## 7. 这些 git 命令到底怎么被执行（run.ts）

前面所有 `runGit(...)` 调用，最终都落到 `run.ts`：

```ts
export const runGitRaw = async (cwd, args) => {
  const proc = Bun.spawn(["git", ...args], { cwd, stdout: "pipe", stderr: "pipe", env: process.env })
  // 等它跑完，读 stdout/stderr，非 0 退出就抛错
}
export const runGit = async (cwd, args) => {
  await awaitWorkGitReady(cwd)   // 等建作品时的后台 git init 完成
  return runGitRaw(cwd, args)
}
```

**大白话**：项目没有用某个"git 库"，而是直接**启动一个 git 命令行子进程**来干活（`Bun.spawn` 就是"启动外部程序"）。`runGit` 比 `runGitRaw` 多一道"等 git 初始化好"，避免作品刚建、`.git` 还没好就去提交导致报错。

> [!tip] 复习：[[09 名词解释#进程内嵌入（in-process embedding）]] 说的是 Session 嵌进来；这里相反——git 是**另起进程**调用的，不是嵌进来的。两种"调用别的能力"的方式，记住区别。

## 8. "未提交改动"列表从哪来（listUncommittedPaths，work-repository.ts:139）

对话栏里那些"待你裁决的 diff 文件"列表，来自：

```ts
const output = await runGit(workRoot, [...gitQuotePathOff, "status", "--porcelain", "-uall"])
const paths = parsePorcelain(output)
```

`git status --porcelain` 是 git 给程序读的"紧凑状态输出"，解析出哪些文件有未提交改动。

> [!note] 一段并发优化的小彩蛋（了解即可）
> 下面一大段 `pendingCache` / `generation` / `inflightKey` 是为了：多个请求同时问"哪些文件改了"时，缓存 1.5 秒（TTL）并合并成一次 git 调用；期间若有人写了文件，就 `bumpPendingGeneration` 让旧结果作废。初学不必深抠，知道"它做了缓存+防并发脏读"即可。

---

## 9. 小结：这一块对应哪条铁律

- **作者即裁判** → Keep/Undo 是作者主动点的，AI 调用链里没有任何自动 commit HEAD 的代码（搜索全仓库也不会有）。
- **确定性归系统** → 路径校验、索引同步、统一门面，都是系统强制执行，不靠 AI"自觉"。
- **作品 = 目录 + git** → `work-layout.ts` 定目录，`finalizeGitRepository` 定 git，二者结合就是"一个作品"。
