# 15 实现深读⑥：检索索引

> [!abstract] 这篇讲什么
> 作者在前端搜"主角第一次出场"，后端怎么在海量 markdown 里全文检索？本项目用**每作品一个 SQLite 索引**（不是 ES/向量库）。核心语义是 spec 要求的"**写后立即可见、Undo 立刻消失**"——靠 ① 讲的唯一提交服务挂索引钩子实现。生词见 [[09 名词解释]]。

---

## 1. 整体结构（Mermaid）

```mermaid
flowchart LR
    COMMIT[Keep/Undo 提交服务] --> HOOK[createIndexedCommitService]
    HOOK --> SYNC[syncWorkIndexPaths]
    SYNC --> IDX[(workId-index.sqlite)]
    SEARCH[searchWorkDocuments] --> SYNC2[syncWorkspace 兜底]
    SYNC2 --> IDX
    IDX --> HITS[searchDocuments 命中]
```

## 2. 核心索引（novel-core/search/search-index.ts）

### 2.1 `openIndex`（search-index.ts:25）
- **做什么**：打开（不存在则建）该作品的 SQLite 索引库。库路径 = `indexPathForWork(worksRoot, workId)` = `{worksRoot}/{workId}-index.sqlite`（search-index.ts:192）。
- **表结构**：`document(path PK, content, updated_at)`（search-index.ts:17）。极简：路径为主键，内容全文存文本，updated_at 记 mtime 用于增量同步。

### 2.2 `upsertDocument` / `removeDocument`（search-index.ts:32 / 39）
- **做什么**：`INSERT ... ON CONFLICT(path) DO UPDATE` 写/覆盖一篇文档；或按 path 删除。
- **这是"写后可见 / Undo 消失"的最小原子操作**：Keep 一篇 → upsert；Undo 一篇 → remove。

### 2.3 `categoryOf`（search-index.ts:43）
- **做什么**：从路径第一段推断分类（正文/大纲/设定…）。搜索可按 category 限定范围。

### 2.4 `locateMatch`（search-index.ts:45）
- **做什么**：在文档内容里找命中行，返回行号 + 该行前 200 字 snippet + 命中位置 anchor（前端高亮用）。找不到则退回"整篇去空白前 200 字"。

### 2.5 `searchDocuments`（search-index.ts:61）—— 真正的查询
- **做什么**：`WHERE content LIKE %needle% OR path LIKE %needle%`，可选 `category` 前缀过滤，`LIMIT` 下推到 SQL（避免全量 hydrate 再切，注释 search-index.ts:71）。
- **返回**：每个命中经 `locateMatch` 生成 `SearchHit`（path/excerpt/snippet/line/anchor/category/tags）。
- **限制**：LIKE 前缀模糊匹配，排名按插入顺序（非相关性排序）——够用即可，不引入 heavier 引擎。

### 2.6 `walkMdFiles`（search-index.ts:107）
- **做什么**：用 `Bun.Glob("**/*.md")` 递归列出作品内所有 markdown 文件。

### 2.7 `syncPaths`（search-index.ts:115）—— 增量同步指定路径
- **做什么**：并发读这些文件的文本内容（`Promise.all` 读），但 SQLite 写入串行（单连接）。文件不存在 → `removeDocument`；存在 → `upsertDocument`。
- **为什么并发读+串行写**：读是 IO 可并行提速，写 SQLite 单连接串行避免竞争。

### 2.8 `syncWorkspace`（search-index.ts:142）—— 全量增量同步
- **做什么**：把索引对齐到磁盘最新状态。
- **逻辑**：① 索引里有但磁盘已删的 → `removeDocument`；② 用 mtime 比对找出"变旧(stale)"的 markdown 重新读；③ `includeUncommitted` 时调 `listUncommittedPaths` 强制刷新未提交脏路径（search-index.ts:163，对应 ① 的 git 未提交列表）。
- **注释关键点**（search-index.ts:139）：**写入已经通过索引钩子实时 sync 了**，syncWorkspace 只是兜底（惰性、mtime 增量），不会每次搜索全量重读正文。

### 2.9 `createIndexSyncHook`（search-index.ts:185）
- **做什么**：返回一个钩子函数 `({workRoot, paths}) => syncPaths`。只在 workRoot 匹配时同步。这就是 ① 提交服务"索引同步钩子"的本体。

## 3. 服务端胶水（novel-server）

### 3.1 `syncWorkIndexPaths`（work-index-sync.ts:9）
- **做什么**：给定若干路径，打开该作品索引库并 `syncPaths` 同步，finally 关库。
- **`createIndexedCommitService`**（work-index-sync.ts:25）：**关键**——用 `WorkGit.createCommitService` 创建提交服务，并把"每次提交后调 `syncWorkIndexPaths`"作为钩子注入。这样 ① 里所有 Keep/Undo/重命名都自动刷新索引 → **写后立即可见、Undo 立刻消失**。

### 3.2 `searchWorkDocuments`（work-search.ts:6）—— 作者侧搜索入口
- **做什么**：参数校验（非空、≤100 字、limit 1–50）→ 打开索引库 → `syncWorkspace`（兜底增量同步）→ `searchDocuments` 查 → 返回命中。
- `SearchQueryError`（work-search.ts:43）：搜索参数错误（缺少词/过长/数量无效）。

> [!note] 与 ① 的闭环
> ① 的唯一提交服务是"所有写入的唯一门"，本篇的 `createIndexedCommitService` 给它挂了索引钩子。所以**任何**经提交服务的写（Keep/Undo/重命名/删除）都会即时反映到搜索——这是"确定性归系统"在检索层的体现：搜索可见性由系统保证，不靠 AI 记得去更新。
